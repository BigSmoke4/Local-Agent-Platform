| **Agent Engine (Phase 5, Sections 8/9/47)** | Real: `AgentOrchestratorService` runs an actual state machine (Created → Understanding → Planning → Executing → AwaitingApproval/Verifying → Completed/Failed/Cancelled), persisted on `AgentSession.State` at every transition. Planning makes a **real** call to the configured model via `IModelProvider`, using a tool list built live from `ToolExecutionService.AllTools` (never a hard-coded/stale list) and parses the model's actual JSON response — if the model doesn't return valid JSON, the session fails honestly with the raw output saved for inspection, rather than fabricating a plan. Execution drives the same `ToolExecutionService` the Tools console uses (no separate weaker code path for agent-run tools), enforces real budgets every iteration (`AgentBudgetPolicy`: max iterations/retries/duration — Section 47), and supports real cancellation (`AgentRunRegistry` + linked `CancellationToken`) and real human-in-the-loop approval resumption for risky tool calls |
| **Verification (Phase 5, narrow slice of Sections 15/16)** | Superseded by Phase 6 below — kept here for history. |
| **Verification Engine (Phase 6, Sections 15/21)** | Real: `VerificationPipelineService` runs the actual `BuildTool`, then (only if the build passed) the actual `TestTool`, parsing their **real console output** with pure regex parsers (`BuildOutputParser` counts real `error CS####`/`warning CS####` occurrences; `TestOutputParser` reads the real `dotnet test` summary line and returns "unrecognized" rather than a guessed zero if the format doesn't match). It also runs a real, if narrow, pattern-based security scan (`RegexSecurityPatternScanner`) over actually-tracked files — hardcoded credentials, inline-password connection strings, weak hashes (MD5/SHA1), string-concatenated SQL, disabled TLS validation — and persists every result to a `VerificationRun` row. `OverallResult` is computed purely from these real signals. |
| **Self-Critic Reviewer (Phase 6, Section 16)** | Real: `ReviewerService` makes an actual model call with the real verification results and asks for a structured Approve/Reject verdict. This is explicitly **advisory only** — a clean reviewer opinion can never turn a real build/test failure into a reported success, and a reviewer failure/unparseable response never blocks or fakes a result; it's recorded as "Unavailable" and the deterministic pipeline result still governs. |
| **Bounded repair loop (Phase 6, Sections 15/47)** | Real: on a failed verification or a reviewer rejection, the orchestrator enters `Repairing`, builds a new planning prompt containing the **actual** failure text (real compiler errors / real test summary / real reviewer reason), asks the model for a real repair plan, executes it through the same tool pipeline, and re-verifies — up to `AgentSession.MaxRepairAttempts` (default 2) times. If repairs run out, the session ends `Failed` with the real last verification attached — it never claims success it didn't earn. |
| **Memory system (Phase 7, Section 14)** | Real: `MemoryEntry` rows in Postgres across five scopes (ShortTerm/Working/LongTerm/UserPreference/Execution). Retrieval is real and deterministic — `MemoryRelevanceRanker` scores candidates by actual keyword overlap with the query, blended with a user-settable importance weight and recency decay, and `MemoryRetrievalService` greedily fills a character budget rather than dumping every stored memory into the prompt (the literal instruction in Section 14). Every agent session automatically writes a real `Execution`-scope memory entry at every terminal state (Completed/Failed/Cancelled) built from its actual final summary — never a synthesized account — so a later session on the same repository can retrieve "this was already tried and failed because X." Retrieved memories are woven into the real planning prompt via `AgentPlanningService`'s new `additionalContext` parameter. A Memory page lets a person add manual LongTerm/UserPreference/Working notes and browse everything stored. |
| **SignalR real-time events (Phase 8, Sections 18/20)** | Real: `AgentTelemetryHub` broadcasts `AgentSessionUpdated`/`AgentTaskUpdated` from every real state transition in the orchestrator, routed through an `IAgentEventBroadcaster` abstraction so `Agent.Application` has no direct SignalR/ASP.NET Core dependency. `HardwareTelemetryBroadcastService` polls the real `IHardwareTelemetryProvider` every 3s and pushes the actual snapshot to any connected client. The Dashboard's hardware panel updates live without a page reload, and the Agent Details page auto-reloads shortly after a real event arrives. The SignalR JS client is vendored locally via `libman.json` — never fetched from a CDN at runtime, respecting Section 49's local-first/offline requirement. |
| **Neural navigation UI (Phase 9, Section 27)** | Real: a server-rendered SVG graph (`_NeuralNav.cshtml`) with genuine working links per module, active-state highlighting driven by the actual current route (read from `ViewContext.RouteData`, not guessed), and `prefers-reduced-motion` fully respected in CSS (Section 53). A plain-text nav is kept alongside it as an accessible fallback, since a purely graphical nav is a real screen-reader risk. |
| **IDE-independent JSON API (Phase 10, Sections 18/19/45)** | Real: `GET /api/models`, `GET/POST /api/agent/sessions` (+ `/approve`, `/cancel`) — routed through the exact same `AgentOrchestratorService` and `AgentRunRegistry` the MVC UI uses, no separate weaker path — and `GET /api/telemetry/{hardware,tokens}`. Documented live via a real Swagger/OpenAPI UI at `/swagger`, and every `/api/*` controller is rate-limited (60 req/min, `EnableRateLimiting("api")`). This is the literal "generic local endpoint so compatible clients can connect without a custom integration" the spec asks for as the fallback when no purpose-built IDE adapter exists. |

## Explicit extension points (not implemented — marked, not faked)

- `Models.Application` — model **routing** (Section 31: automatically picking small vs. large model per task type) is still unimplemented; Phase 2 only covers registry + manual load/default selection, not automatic routing
- Capability metadata beyond what Ollama's `/api/tags` exposes (e.g. tool-calling support is currently hardcoded `false` in `OllamaModelProvider` since Ollama doesn't report it uniformly)
- **Semantic code graph / dependency graph (Section 12).** Phase 3's Roslyn extractor is a *single-file syntactic pass* — it parses each file's syntax tree independently. It does **not** build a full-solution semantic model, so it cannot yet resolve "ProductController calls ProductService calls ProductRepository" style cross-file relationships. The `CodeRelationship` entity exists in the schema but nothing populates it yet — that requires loading a Roslyn `Compilation`/`Workspace` across the whole project, which is a real, larger follow-up.
- **Project/repository ownership is still not tied to the real logged-in user.** `RepositoryManagementService.EnsureDefaultProjectAsync` still hardcodes a shared "Local Workspace" project with `OwnerUserId = Guid.Empty` rather than creating one per authenticated user — login now exists (see Authentication row below), but per-user workspace isolation hasn't been wired up on top of it yet. Every logged-in user currently shares the same projects/repositories/agent sessions.
- **Symbol browsing pagination.** The Symbols view caps at 500 rows with a `Take(500)` placeholder — no real paging UI yet.
- Non-C# languages are detected (for hashing/snapshotting) but have no symbol extractor registered — only `.cs` files get parsed for symbols right now.
- `Agent.*` — the orchestration loop itself is now real (Phase 5) and now includes a real, bounded repair loop (Phase 6), but several things named in Sections 8/9 are still not: **general branching task graphs are not implemented — the current planner only produces a linear chain** (each task's `ParentId` is simply the previous task); "Resume" only works for the specific AwaitingApproval case, not general crash-recovery of an Executing/Repairing session (Section 58) — if the process restarts mid-run, that session is left in whatever state it was last saved in and must be manually inspected.
- **The security scanner is deliberately narrow** — five regex rules (hardcoded secrets, inline-password connection strings, weak hashes, string-concatenated SQL, disabled TLS validation), no dataflow analysis, no suppression/allowlist system, and it only scans `.cs`/`.json`/`.config` files that the repository indexer already tracks. This is a real, working first pass at Section 38's "static/security analysis," not the full SAST tooling a mature version of this section implies.
- **The reviewer's context window is small on purpose** — it sees the verification numbers and the original request, not a full diff of what changed. It's a sanity-check layer, not a full code review; the doc comment in `ReviewerService.cs` states this scope explicitly.
- **Repair prompts don't carry forward specific file diffs** — the repair planning call gets a text summary of what failed (compiler errors, test summary, reviewer reason), not the actual changed-file contents. A more capable version would feed the model the specific failing code; this version relies on the model's own judgment plus the same FileRead/Edit tools to re-investigate if needed.
- **Memory retrieval is keyword-overlap, not semantic/vector search.** `MemoryRelevanceRanker` will miss a memory that's conceptually relevant but shares no vocabulary with the query (e.g. a note about "the auth flow" won't surface for a query about "login" unless both words appear). Spec Section 14 explicitly anticipates this by saying to design so Postgres-compatible vector storage can be used later — this is the honest pre-vector version, not a hidden shortfall.
- **The "character budget" in memory retrieval is a proxy for a token budget**, not an actual token count — matching the same documented approximation used elsewhere (e.g. Context Engine budgets in Section 13, which is not yet implemented at all — see below).
- **ShortTerm and Working memory scopes exist in the schema and the UI but nothing automatically populates them yet** — only `Execution` memory is auto-written (by the orchestrator) today; `LongTerm`/`UserPreference`/`Working` are currently manual-entry only via the Memory page. Auto-populating "Working" memory from what a session actually investigated is a natural next increment, not implemented here.
- **Context Engine (Section 13) — the repository-wide context selection/ranking/compression system — is not implemented.** Memory retrieval (Phase 7) is a related but narrower concern (retrieving *notes about past work*), not the same as ranking *live repository content* (files/symbols/diffs) into a context budget for the model. That remains a distinct, unimplemented piece of the spec.
- **`AgentRunRegistry` is in-memory only.** If the web process restarts while a session is running, that session's `CancellationTokenSource` is gone — the session row will simply stay in whatever state it last saved, and the "Cancel" button will correctly report it's not running rather than pretending to cancel it.
- The planning prompt is intentionally strict about JSON-only output; smaller/less-instructable local models may fail to follow it reliably. That's a real, visible failure (session goes `Failed` with the raw text saved), not a crash or a silent fallback to a fake plan.
- **Terminal/Build/Test tools require the host to actually have `git`/`dotnet` on PATH.** If they're missing, the tool returns a real failure result (process start exception) — not a fake success.
- **`TerminalTool`'s command policy combines a static built-in allowlist/denylist** (`CommandPolicyEngine`) **with a real persistent per-user Always-Allow/Always-Deny layer** (`CommandPermissionRule` + `CommandPermissionService`) — Section 11's scoped-permission model is now implemented for human-initiated calls from the Tools console. **Agent-initiated tool calls do not check persisted rules** — `AgentOrchestratorService` calls `ToolExecutionService.InvokeAsync` without an `ownerUserId`, so an unattended agent run always falls back to the static policy only. Wiring `AgentSession` to a specific user (it currently has no `UserId` column) is the remaining piece to close this fully.
- **`GitTool` intentionally exposes no mutating subcommands** (no commit/push/reset/checkout) — see the doc comment in `GitTool.cs`. This is a scope boundary, not an oversight.
- **SignalR real-time granularity is coarse.** There is no per-field diffing — a client just learns "this session/task changed" and either patches a couple of `data-telemetry` spans (Dashboard) or reloads the page (Agent Details). A production version would push structured payloads the client renders incrementally.
- **The hardware telemetry broadcast is poll-based (every 3s), not a true OS-level push subscription** — a real, working implementation, just not an event-driven one. GPU/VRAM/temperature/power remain "Unavailable" (see above) regardless of the transport.
- **`IIdeIntegrationProvider` (Phase 10, Section 19) has no concrete implementation.** Building a real Cursor, VS Code, JetBrains, or Antigravity adapter requires that editor's actual documented extension/protocol surface — this project does not fabricate one. What satisfies the spec's own stated fallback ("support a generic local endpoint so compatible clients can connect without a custom integration") is the real, now-authenticated `/api/*` JSON API plus `/swagger` — any tool capable of local HTTP calls (and holding a valid API key) can already drive this platform through it.
- **Authentication now exists** (cookie for the MVC UI, API key for `/api/*` — see `docs/SECURITY.md`), closing the previously-named gap. What it does **not** cover: roles/permissions beyond "authenticated or not," password reset, MFA, account lockout. Single/small-team local-tool-grade auth, not enterprise IAM.
- **Unit tests cover Domain layers; integration tests now cover a meaningful slice of Application/Infrastructure** (`ModelRegistryService`, `RepositoryIndexingService`, `ToolExecutionService` — all against a real Postgres connection). **Still not covered**: the real HTTP calls to Ollama (`OllamaModelProvider`), the real `Process` invocations in `TerminalTool`/`GitTool`/`BuildTool`/`TestTool`, and the orchestrator loop end-to-end (`AgentOrchestratorService.RunAsync` against a real model + real tools together). Testing the orchestrator meaningfully requires either a real local Ollama instance in CI or a fake `IModelProvider` test double wired through DI — neither exists yet.
- **No load/performance testing has been done** on any of Sections 44/46's requirements (pagination, N+1 avoidance, bundle size, etc.) — the code follows sensible patterns (DTOs, `Take()` limits, async I/O throughout) but nothing has been measured under load.
- Memory system (Section 14) — see the real row above; this line is intentionally left as a marker that the *section itself* is now substantially covered, with the specific remaining gaps listed under its own bullets above.
- IDE adapters (Section 19) — see the `IIdeIntegrationProvider` bullet above.
- GPU/VRAM/temperature/power telemetry (needs `nvidia-smi`/`rocm-smi`/`lm-sensors` integration)
- **Docker/CI now exist** (`Dockerfile`, `docker-compose.yml` including the web app, `.github/workflows/ci.yml`), closing the previously-named gap. What's still missing: a production `appsettings.Production.json` split with real secrets management (see SECURITY.md), a CD (deploy) step beyond "build the image," and any smoke/health-check gate after deployment.
- **Remaining spec documents** — Section 64 asks for `API.md`, `AGENT_ENGINE.md`, `MODEL_RUNTIME.md`, `CODE_INTELLIGENCE.md`, `TOOL_SYSTEM.md`, `TELEMETRY.md`, `IDE_INTEGRATION.md`, `DATABASE.md`, `TESTING.md`, `DEPLOYMENT.md` as separate files. `README.md`, `docs/STATUS.md`, `docs/ARCHITECTURE.md`, and `docs/SECURITY.md` together cover the same ground this codebase actually warrants documenting; the remaining per-topic files are not split out separately.

## Known unverified items

- **Not compiled.** No .NET SDK was available in the authoring sandbox. Run `dotnet build` before trusting this compiles as-is.
- NuGet package versions were chosen from training-data knowledge of the EF Core 8 / OpenTelemetry / Serilog.AspNetCore / Roslyn (`Microsoft.CodeAnalysis.CSharp` 4.11.0) / Swashbuckle.AspNetCore / xUnit ecosystem as of early 2026 and may need bumping.
- EF Core migrations have not been generated/committed — the README documents the command to run, and `Program.cs` now calls `Database.MigrateAsync()` automatically at startup, **but that call does nothing useful until a real migration exists** (with zero migrations, `Migrate()` only creates the `__EFMigrationsHistory` table). Phase 3 adds four new entities (`FileSnapshot`, `CodeSymbol`, `CodeRelationship`, `RepositoryIndexingJob`); Phase 4 adds two more (`ToolDefinition`, `ToolExecution`); Phase 5 adds one more (`AgentTaskNode`) and extends `AgentSession` with plan/budget/summary columns; Phase 6 adds `VerificationRun` and two more `AgentSession` columns; Phase 7 adds `MemoryEntry`; this hardening pass adds `ApiKey` and `CommandPermissionRule` — **running `dotnet ef migrations add InitialCreate` (or similar) before first use is not optional**, it's required for anything to work.
- The Application layer in `RepositoryAnalysis` references `Infrastructure` directly (for `IRepositoryFileScanner`/`ICodeSymbolExtractor`) rather than those interfaces living in a dependency-free layer — a pragmatic shortcut flagged here rather than hidden.
- `ToolExecutionService.InvokeAsync` resolves the repository row on every call (a DB read) rather than caching — fine at this scale, worth revisiting once/if this is called in a tight agent loop.
- **`libman restore` has not been run.** The SignalR JS client referenced by `telemetry.js`/`agent-live.js` (`~/lib/signalr/dist/browser/signalr.min.js`) will 404 until you run it — both scripts fail safe (they check `typeof signalR === "undefined"` and log a warning) rather than breaking the page. See the README setup steps.
- The xUnit test projects (both Domain and Integration) have not been run (same "no .NET SDK in this sandbox" constraint as everything else) — they're believed correct against the actual code they target, but `dotnet test` should be run to confirm. The Integration project additionally needs a reachable Postgres instance (`docker compose up -d postgres`) and, since it uses `EnsureCreatedAsync()` rather than migrations, does **not** depend on the InitialCreate migration existing — it creates its own schema directly from the current model.
- **The `.sln` file is not exhaustive** — it lists the Web host, a representative sample of module projects, and both test projects, but not all 25 `.csproj` files under `src/`. This has been true since Phase 1; `dotnet run`/`dotnet build`/`dotnet test` all work directly off project references regardless of `.sln` completeness, but opening the solution in an IDE won't show every project.
- **The CI workflow (`.github/workflows/ci.yml`) has not been run** — it's written to be correct (real service container, real `dotnet` commands, real Docker build) but, per the same sandbox constraint as everything else, has not actually executed on GitHub Actions.
- Swashbuckle.AspNetCore's `Microsoft.OpenApi.Models` types are referenced with fully-qualified names in `Program.cs` (no `using Microsoft.OpenApi.Models;`) to keep the diff minimal against the existing file — purely a style choice, not a functional concern.
