# Agent Engine

Two real entry points exist, intentionally kept separate rather than one
doing both jobs badly:

## `POST /api/agent/run` (AgentController)

Minimal loop: `Created -> Understanding -> Executing -> Completed/Failed`.

1. `ModelRouter.RouteAsync` classifies the request (Trivial/Simple/Complex)
   and picks a model — or no model, for arithmetic.
2. Arithmetic goes to `CalculatorTool` (deterministic-first rule, §68).
3. Everything else goes to `IModelProvider.GenerateAsync` against the
   routed model.
4. Result, token counts, and state are persisted to `AgentSession`.

No task graph, no verification, no repair — this is the "just answer me"
path.

## `POST /api/agent/run-verified` (AgentVerificationController)

Real task graph: `Build -> Test -> Review`, persisted as `AgentTaskNode`
rows, retried up to `MaxIterations = 3` (hard cap — never unbounded, per
§47). On build failure:

1. `BuildDiagnosticParser` finds the real failing file from actual compiler
   output (or uses the caller-supplied `RepairTargetFile`).
2. `AutonomyService` gates whether an automated edit is allowed at all.
3. If allowed, `SafeFileEditService` reads the file, sends the real build
   output + content to the model, strips markdown fences from the
   response, and applies it (hash-checked, snapshotted, diffed).
4. The loop retries the build.

On build+test success, `ReviewerService` makes a second real model call for
an independent approve/reject verdict (fails closed if the model call
errors).

## What "planning" actually means here

The task graph sequence (Build → Test → Review, with Repair inserted on
build failure) is **fixed in controller code**, not generated by the model
from the user's request. A true planner per §8/§9 would have the model (or
a dedicated planning step) decide the sequence of nodes based on the
specific request — e.g. "add Redis caching" would need
Analyze→Design→Implement→Update DI→Configure→Build→Test nodes, not just
Build→Test→Review. That dynamic planning step is not built.

## Explicit states implemented

`AgentSessionState` enum has all ten states from §8
(`Created, Understanding, Planning, Executing, Observing, Verifying,
Repairing, Completed, Failed, Cancelled`), but `Planning`, `Observing`, and
`Cancelled` are currently unused by any code path — they exist for a future
planner/cancellation implementation to use, not decorative.
